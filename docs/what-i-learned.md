# 코딩 에이전트 구현 회고 — 무엇을 배웠는가 (Study Wiki)

Anvil을 직접 설계·구현·개선하면서 배운 **코딩 에이전트 엔지니어링의 핵심 원리와 시행착오**를 위키 형태로 간단히 정리한 문서입니다.

---

## 1. 코딩 에이전트의 성능은 '모델'만큼 '하네스(Harness)'가 결정한다

일반 챗봇은 텍스트 입출력만 다루지만, 코딩 에이전트는 **파일시스템·셸·프로세스·사용자 승인 상태**와 끊임없이 상호작용합니다.

- **배운 점**: 프롬프트를 길게 쓰는 것보다 **모드별 실행 환경 자체를 물리적으로 분리**하는 것이 훨씬 안전하고 예측 가능했습니다.
  - 예: 읽기 전용인 `Ask` 모드에서는 프롬프트로만 "수정하지 마라"고 지시하는 대신 아예 `execute` 도구를 빼고 읽기 전용 백엔드(`FilesystemBackend`)를 마운트해 오작동 가능성을 원천 차단했습니다.
  - 반대로 계획이 승인된 뒤(`plan_approved=True`)에는 메타문자가 없는 순수 테스트 명령(`pytest`, `ruff`, `npm test` 등)의 불필요한 승인 팝업을 없애 에이전트가 막힘없이 검증 루프를 돌 수 있게 했습니다.

---

## 2. 도구를 늘리기보다 '점진적 노출(Progressive Disclosure)'을 써야 한다

기능을 추가할 때마다 전용 도구(Tool)를 계속 늘리면 모델이 매 턴 읽어야 하는 도구 스키마 토큰이 커지고 도구 선택 정확도가 떨어집니다.

- **배운 점**: 코어 도구(`ls`, `read_file`, `write_file`, `edit_file`, `glob`, `grep`, `execute`, `ask_user`, `task`)는 최소한으로 유지하고, 온보딩 문서 작성(`codebase-onboarding`)이나 검증 절차(`verify`), 외부 `skills.sh` 패키지는 **`SKILL.md` 파일 기반 점진적 노출**로 풀었을 때 구조가 훨씬 단순해졌습니다.
- 대량의 파일 탐색이나 코드 리뷰처럼 컨텍스트를 많이 소모하는 작업은 **읽기 전용 서브에이전트(`explorer`, `reviewer`)**로 분리해 메인 에이전트의 문맥 창을 깨끗하게 유지할 수 있었습니다.

---

## 3. 인간 개입(HITL)은 평문 질문이 아니라 '상태가 보존되는 인터럽트'여야 한다

에이전트가 애매한 상황에서 채팅창에 평문으로 질문 3~4개를 쏟아내면 사용자가 답하기도 불편하고 에이전트 흐름도 쉽게 꼬입니다.

- **배운 점**: LangGraph의 `interrupt()` / `Command(resume=...)`를 활용해 실행 그래프를 일시 정지시키고, 프론트엔드 입력창 위에 **구조화된 질문 카드(`ask_user` — 추천 선택지 표시·단축키·직접 입력·건너뛰기)**와 **계획/셸 승인 배너**를 띄우니 협업 흐름이 명확해졌습니다.
- 인터럽트 페이로드를 SQLite 세션 상태에도 함께 기록해 두면 브라우저를 새로고침하거나 서버를 재시작해도 승인/질문 대기 상태가 그대로 유지됩니다.

---

## 4. 자율 검증 루프(Verification)와 '검증 기준 독립성'

에이전트가 코드를 고친 뒤 스스로 검증하게 만들 때 두 가지 현실적인 함정이 있었습니다.

1. **무한 재시도와 테스트 약화**: 테스트가 실패할 때 에이전트가 원인을 파악하지 못한 채 무작정 재시도하거나, 심지어 테스트/린트 규칙 파일을 고쳐서 통과시키려는 시도를 할 수 있습니다.
2. **도구 출력 포맷 차이**: 프레임워크(`deepagents`)가 반환하는 종료 코드 포맷(`[Command failed with exit code 1]` 및 `ToolMessage.artifact["exit_code"]`)을 정확히 읽지 못하면 실패한 테스트를 성공으로 오판할 수 있습니다.

- **배운 점**:
  - **Three-Strike 규칙**: 검증 명령이 연속 3회 실패하면 재시도를 멈추고 실패 증거와 원인 가설을 사용자에게 보고하도록 미들웨어에서 제어했습니다.
  - **검증 통과 후 재수정 감시**: 테스트 통과 직후 다시 파일을 수정하면 기존 `Verified` 스탬프를 즉시 무효화해 재검증을 유도했습니다.
  - **검증 기준 보호 (*"Changes can't modify their own checks"*)**: `AGENTS.md`, `REVIEW.md`, `.github/workflows/*`, 아키텍처 경계 테스트 파일을 에이전트가 수정하려 할 때는 자율 모드(`Auto`)라도 반드시 사용자 승인을 거치도록 막았습니다.

---

## 5. 코딩 에이전트의 Revert는 '파일 + DB + LLM 기억' 3계층을 함께 되감아야 한다

처음에는 Revert를 단순히 Git 워킹트리나 파일만 이전 상태로 돌리는 기능으로 생각하기 쉽습니다.

- **배운 점**:
  - 사용자가 아직 Git 커밋을 하지 않은 상태에서 턴 1(성공) → 턴 2(실패)를 실행한 뒤 턴 2만 되돌리고 싶을 때 `git checkout`을 쓰면 턴 1의 작업까지 날아갑니다. 이를 해결하기 위해 매 턴 시작 시 **콘텐츠 주소화(SHA-256) 스냅샷(`TurnCheckpointStore`)**을 남겨 Git 커밋 없이도 원하는 턴 시점으로 정확히 복원했습니다.
  - 더 중요한 점은 **파일만 되돌리면 에이전트의 체크포인트 기억에는 여전히 되돌려진 코드가 남아 있어 다음 대화에서 환각(Hallucination)이 발생**한다는 것이었습니다. 따라서 **① 파일 복원 → ② SQLite 메시지 절삭 → ③ LangGraph 스레드 초기화 및 이전 대화 재주입(`prior_messages`) + 프롬프트 입력창 복원**까지 3계층을 맞춰야 진짜 Revert가 완성됩니다.

---

## 6. 유지보수를 지키는 도메인 경계와 UI 상태 분리

구현 규모가 커지면서 겪은 설계 교훈들입니다:

- **브랜드 이름과 인프라 분리**: 초기에는 저장 폴더, DB 파일명, 환경변수, 테마 이름에 프로젝트/사용자 이름 접두어를 붙였는데, 이름을 바꾸려 하자 수십 개 파일이 연쇄 수정되었습니다. 제품 이름은 `APP_NAME` 상수 한 곳에만 두고 내부 경로(`.data/sessions.db`), 환경변수(`LOG_LEVEL`), 테마(`workbench`)는 **역할(Role) 기반 이름**으로 짓는 것이 유지보수에 훨씬 유리하다는 점을 체감했습니다.
- **AST 테스트로 강제하는 DDD 경계**: 문서로만 "도메인 간 참조 금지"라고 적어두면 금방 깨지지만, `ast` 모듈로 import 트리를 검사하는 테스트(`test_architecture_boundaries.py`)를 두니 리팩토링 내내 경계가 한 번도 무너지지 않았습니다.
- **속성 기반 불변식(Property/Invariant) 테스트**: 시드 기반 무작위 파일 생성·수정·삭제 시퀀스를 돌린 뒤 역순으로 Revert했을 때 초기 파일 트리와 100% 일치하는지 검증하는 불변식 테스트 덕분에 빈 디렉터리 정리와 경로 탈출 방어(`PathEscapeError`) 엣지 케이스를 확실히 잡을 수 있었습니다.
- **원본 보존 + 순수 함수 파생 UI**: 연속된 `ls`/`grep`/`read_file` 호출을 UI에서 하나의 접이식 그룹(`ExplorationGroup`)으로 합칠 때, 백엔드 스트리밍 스키마나 원본 메시지 배열을 건드리지 않고 렌더링 직전 순수 셀렉터로만 변환하니 디버깅과 단위 테스트가 모두 깔끔해졌습니다.
